# 精简复验：保留真实宿主与 Skill 调用

适用场景：已经完成相应环境与产物核对，后续只确认 Skill 和工作流入口仍可工作。首次交付仍按 [12 步文档](../MANUAL-ACCEPTANCE.md) 执行；精简结果不记为新一轮完整 12 步通过。四个工作流不进入 CI、定时任务或自动串联脚本。

## 每次先检查环境

在真实 Codex 或 Claude Code 新建短对话，提供被测项目路径、已安装 Skill 版本和本轮目标。核对操作系统、宿主版本、Skill 提交、runtime-check 对齐结果、实际保存的 Agent/模型，以及源码和所复用测试资产是否变化。沿用已初始化配置，不重建环境、不重新搜索安装已有包。安装、准备和只读核对可以使用脚本。

业务入口必须保留：**真实宿主 → sublang Skill → setup 返回的 SubLang CLI → 原工作流 → 真实内层 Agent**。保存实际调用记录；脚本直调 CLI 只能说明 CLI 能运行，不能证明宿主会正确调用 Skill。

## 步骤 9：入口复验

在尚未执行提取的最小 Hello 项目中，发送：

```text
使用 sublang 调用 extract-specs，只验证最小 Hello 项目的现状提取入口。
不修改源码和测试，按原工作流执行；到第一个需要人工确认的 Gate 时展示材料并停止，不提前批准。
简短报告实际宿主、Skill、包和引擎版本、内层 Agent/模型、会话及当前状态。
```

核对工作流确实启动、原独立委派审查实际发生，并到达预期 Gate。记为“入口复验通过，完整工作流等待确认”；不能记提取已完成。若目标是完整提取验收，仍需继续原 Gate、审查、lint 和终态检查。已完成过的项目不为复验重置历史或重复提取；选择另一个已有最小样例，或复核保留的实际入口证据。

## 步骤 12：单场景复验

由操作者提供已经核对的任务/AT、实现版本及相关产物位置，发送：

```text
使用 sublang 的 acceptance-orchestrate 对已有 --upper 验收任务做一次最小复验。
由 sublang 返回的 SubLang CLI 调用，不切换到 app-delivery-acceptance 独立 Skill 或独立 Playbook CLI。
复用本轮提供的已冻结定义、运行环境、项目、单个用例和已接收评估；先确认其版本和绑定仍有效。
只对已有 --upper 正常场景新增一次正式执行、原独立复审和短报告，coverage 关闭，修复预算为 0。
不新建 AT、不重新生成场景/用例、不改产品代码、不重复评估仍有效的用例。发现绑定失效、模型调用失败或需要扩大范围时保留实际状态并停止。
请简短报告结果与证据位置，不读取完整旧对话、不输出整份长报告。
```

外层宿主负责按公开合同传递原任务身份和新的请求标识，工作流负责检查持久状态与未决效果。不能用重放旧请求代替一次新执行，也不能用上次收据冒充本次结果。

核对：本次真实 Skill/CLI 调用、选中入口及实际模型；一次新正式执行的收据与测试结果；原独立复审通过；报告中的单场景统计与实现/测试绑定一致。只保存必要证据，不重复全量历史扫描和已验证的不变文件审计。

## 记录边界

- 分别记录首次完整验收、恢复后通过、精简复验、等待确认和提供商失败。
- 不省略真实内层调用，不替换模型或修改权限来制造通过。
- 未实际执行的系统/宿主组合记 NOT_RUN；原始失败保留。
